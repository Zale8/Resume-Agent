# 根因审计：为什么「总套用上一份、排版反复出问题」（2026-09-21）

> 背景：本项目早期由 AI 编程工具代写，后续实践中反复出现以下症状。
> 本文是一次系统性架构审计的结论，用于追溯成因、记录修复、留存待办。
> **本文不含任何个人数据**（不含真实姓名 / 公司 / 学校 / 路径）。
>
> **状态（2026-09-21 当日二轮修复）**：R3 / R4 / R5 已由 v0.9.0 从**机制**上缓解
> （`design.json` 落盘 + `content_parser` + `fitting`），S1 / S3 的直接来源已消除。
> R1 / R2 / R6 仍待产品方向决策（见 §3）。详见 §2.1。

---

## 0. 症状（本次审计要解释的现象）

| 编号 | 症状 |
|---|---|
| **S1** | 生成新简历时**总套用上一份的模板** |
| **S2** | 没有**自主编排和创新审美**的能力 |
| **S3** | 每次输出的结果**不是排版就是内容和效果上的问题** |

症状不在"文字措辞"层——`agent_entry.md` 与 `prompts/system_prompt.md` 都已明确写着
「禁止复制上一份公司的生成脚本只改颜色」「每次重新设计」「不使用固定模板」。
问题在于**这些规则与项目其它部分互相矛盾，或缺少机制支撑**。

---

## 1. 根因

### R1 「禁止参照上一份」与「必须参照上一份」并存 → S1 / S2

同一份规范里同时存在相反指令：

| 位置 | 指令 |
|---|---|
| `AGENT.md` §六 第 7 条 | 「下一次生成的设计输入是当次重新确定的 Design Decision，**不读取上一份 notes**」 |
| `AGENT.md` §十二 | 禁止「**根据上一份生成简历继续生成下一份简历**」 |
| `AGENT.md` §十四 | 「历史成品 DOCX 不是模板、也不是数据源，**不得复制其文件直接改字复用**」 |
| **但** `AGENT.md` §九 自检注 | 「生成任务若涉及与 Golden Sample 相同的视觉范式，**应参考其视觉规范**、验收规则……」 |
| **且** `agent_entry.md` §5.1.2 | 「✅ **视觉验收规则的来源之一**」 |

**后果**：Golden Sample 是项目里**唯一被明文授权"可以参考"的历史产物**，
而它同时携带一套完整的、可直接执行的视觉参数（配色值、照片尺寸、页边距、浮动坐标）。
在"每份都要重新设计"这条无机制保障的规则面前，它自然退化为事实上的母版
——**母版体系虽已于 v0.6 退役，却以 Golden Sample 的形式原地复活**。

> 这正是 S1 的制度性来源：规则要求"不看上一份"，但唯一被允许看的东西就是一份上一份。

### R2 DesignSpec 声明的设计空间 ≫ 渲染器的实际能力 → S2

`design/consumption.py`（字段消费矩阵，项目自建）当前 **165 条登记**：

| 状态 | 条数 | 占比 | 含义 |
|---|---|---|---|
| `consumed` | 61 | 37.0% | 渲染链路真实读取并进入 DOCX |
| `partially_consumed` | 21 | 12.7% | 仅在部分范式/取值下生效 |
| `fallback`（schema_gap） | 1 | 0.6% | Spec 无此概念，恒回退骨架 Profile |
| **`unconsumed`** | **82** | **49.7%** | **零读取点；赋值不产生任何视觉变化** |

去重后 **78 个字段路径完全没有消费点**，且其中大量是"设计维度"级的字段：

- `grid.column_ratio`（三范式全是 unconsumed）→ 列宽比例由 `_LAYOUT_CONFIG` 骨架常量硬编码
- `header.type` / `header.height` / `header.background_role` / `header.photo_zone` → Header 形态硬编码
- `section.icon.*`（3 个）→ 注释原文「**无图标渲染能力**」
- `section.title_color_role` / `section.title_weight` / `typography.weights.body`
  → 注释原文「**硬编码 ink / 硬编码 regular**」
- `achievement.*`（6 个）→ 注释原文「**全仓无成果横幅渲染代码**（P1 `enabled=True` 静默落空）」
- `photo.position` / `photo.container` / `photo.crop_allowed` → 「零读取点」「无裁切流水线」
- `colors.page_background` → 「无 `w:background`/底色渲染消费点」（**已于 v0.8.2 修复**）
- `density.level` → 「自适应密度引擎未建立」

**后果**：Agent 在 DesignSpec 里"做设计"时，**近一半的决策不会产生任何视觉变化**，
而且不会报错——`evaluate_unconsumed()` 只产出**非阻断 WARNING**。
Agent 得不到"我改了但没用"的反馈，只会观察到"改了也没变化"，
于是收敛到"只用确定能生效的那几十个字段"，而那些字段 Preset 已经填成了固定值
→ **等价于每次都在复用同一套数值**（S2 的直接机制）。

雪上加霜的是矩阵的维护规则第 3 条：

> 「本模块**不新增任何 Renderer 能力**——矩阵只暴露契约缺口，**不填补缺口**。」

即项目建立了一个"缺陷登记册"，并明文规定不修。

### R3 所有"可复用物"都被规则禁止，只剩上一份脚本 → S1

> **✅ 已缓解（v0.9.0）**：Design Decision 落盘为 `design.json`（每份新建、缺文件拒绝、
> 无默认兜底）；内容层有了正式解析器 `content_parser.py`。
> 「唯一可留存物 = 上一份脚本」这一死角不再成立。

规则设计上的死角：

| 可复用的东西 | 规则怎么说 |
|---|---|
| 设计决策 | `agent_entry.md` §5.1：「**对话内明确即可，不新建任何决策文件**」→ 会话结束即丢失 |
| `generation_notes.md` | `AGENT.md` §六：「**不是机器可读的决策输入**」→ 禁止读取 |
| 历史成品 DOCX | `AGENT.md` §十二 / §十四：不是模板、不是数据源 |
| 母版体系 | 已于 v0.6 整体退役 |
| **上一份的临时生成脚本** | `AGENT.md` §十三：**未定稿期间保留同一脚本用于迭代，不重写** |

**结论**：流程上唯一被允许留存、且携带完整设计参数的实物，**恰恰就是上一份的临时脚本**。
于是"复用上一份"不是懈怠，而是当前规则约束下的**唯一可行路径**。

此外，内容层 `resume.md` **没有正式解析器**（`src/` 中 grep `parse_resume_md` 零命中），
解析逻辑写在每份的一次性脚本里 → 跨份之间**唯一留存的产物仍是上一份脚本**，
形成闭环。

### R4 验证闭环几乎为零 → S3

> **✅ 已缓解（v0.9.0）**：`fitting.py` 提供八维 QA（`QaReport`）+ 确定性 auto-fit
> 收敛梯；`check_pages.py` 三处硬缺陷已修（委托修正后的估算器）；
> `measure_pages()` 返回真实口径来源，不伪造页数。

八个质量维度中，只有一项有端到端自动化覆盖：

| 维度 | 自动化检查 | 说明 |
|---|---|---|
| 页数 | ❌ | `RULE_TARGET_PAGES` 只断言 `page.target_pages == 1` 这个**字面字段**，与真实页数无关；`count_pages_com` 仅被一次性脚本调用，产品代码零调用 |
| 末行位置 | ❌ | 全仓无代码 |
| 溢出 | ❌ | `check_pages.py:109-113` **不管溢出与否永远 `return 0`** |
| 寡行（末行 1–2 字） | ❌ | `widow_control` 是 Word 的跨页孤行控制，与"末行只剩一个字"无关 |
| 内容密度 | ❌ | 仅消费矩阵登记，无度量 |
| 边距安全区 | ❌ | Validator 只拦**负值**；`page.safe_area.*` 全部登记为 `unconsumed` |
| 字号下限 | ⚠️ 半 | 只校验 Spec 声明值，header_meta / contact 等 run 不在范围 |
| 照片变形 | ✅ | 声明层 + 渲染层 + 回归测试，覆盖良好 |

而唯一的估算工具 `scripts/check_pages.py` 本身有三个硬缺陷：

- `:74` 只遍历 `wp:inline`，**浮动照片 `wp:anchor` 完全漏检**（而本项目主用浮动照片）
- `:79` 单位换算写错（`int(cx)/12700` 已是 pt，又乘 `72/(2.54*20)*10` ≈ ×14.17）
- `:109-113` 永远返回 0，无法作为门禁信号

**后果**：页数、寡行、溢出、边距安全区**只能靠人肉发现**（S3 的直接来源）。

### R5 内容层契约只有示例，没有校验 → S3 / S1

> **✅ 已缓解（v0.9.0）**：`content_parser.py` 把「识别不到一律静默丢弃」改为
> 显式三档诊断（ERROR / WARNING / INFO），并对 `resume_writer.md` 的**多种合法写法**
> 做容忍（章节别名表、条目标题四种写法、个人信息两种内联写法）。

`prompts/resume_writer.md` 给出的 `resume.md` 示例与解析脚本、历史产物**三方不一致**：

| 项 | prompt 示例 | 解析脚本期望 | 历史产物 |
|---|---|---|---|
| 技能+证书标题 | 合并 `## 专业技能 / 证书奖项` | 分开精确匹配 | 有的合并、有的拆开、有的用 `## 荣誉奖项` |
| 优势段标题 | `## 个人优势` | 兼容 `个人简介`/`个人优势` | 另有 `## 自我评价`（不在兼容列表） |
| 个人信息 | 三列表格 | 按 `cells[0]` 取字段 | 两列表格 / 无表格纯 bullet |
| 条目标题 | `### 公司 - 岗位（时间）` | 正则要求半角 ` - ` + 全角 `（）` | 有的用 `｜` 分隔、日期带空格 |

**且偏差的后果几乎全是静默丢内容**（解析器无 `else` 分支），
**只有"姓名解析不到"会报错**。同类问题也存在于 `data_loader.py`：
键名/标题层级假设严格，且全文件**无一处 `raise`**（docstring 自述"返回 None 或空列表"）。
已实测：某经历文件用 `### 项目结果`（H3）而解析器只认 `## 项目结果`（H2）
→ 整张量化数据表静默丢失；而对应单测能通过，**因为 fixture 用的是 H2，与真实文件格式不一致**。

### R6 守卫的"作者身份"通道绕过了用户自己的敏感词表 → 数据隔离的实质缺口

`tests/check_privacy.py` 的敏感词**不在仓库内**（从仓库外 `99_配置/privacy_terms.txt`
读取），这个设计是对的。它检查 A 工作区文件 / B 提交历史文件 / C 提交信息 / D 被忽略文件，
四项都走词表比对。

但 **E「提交作者身份」不走词表**——它只用通用的 `email_is_personal()` 判断，
并在命中时写成"弱提示"（`:264-265` 注释：「这是用户自己的 git 身份，不算简历数据泄漏」）。

问题在于：**用户的敏感词表里明确列着本人的个人邮箱**（"联系方式"节）。
即用户已声明该邮箱是需要保护的敏感信息，而"作者身份"恰恰是它进入 Git 的**唯一通道**，
却唯独在这一项上不查词表 → **词表对邮箱的约束形同虚设**。

实测后果：仓库 **全部 28 个提交的作者邮箱都是该个人邮箱**，而产品仓库的设计前提是
"可以进入 Git"（`README.md` / `docs/README.md` 均声明可公开）。
审计输出该条为 `⚠️ 提示项（不判失败）`，因此 `commit.py` 不会阻止它继续累积。

> 就"是否属于简历数据泄漏"而言，原注释的技术判断没错（git 身份不来自简历库）。
> 但从"用户已把它列为敏感词"这一权威意图出发，当前判定是**过宽**的。
> 修法涉及用户的外部账号（该用什么 noreply 邮箱）与历史重写，**不属于工具能替用户决定的事**，
> 故列入待决策。

## 4. 一句话总结

> 项目**不缺规则，缺的是让规则成立的机制**。
> 它写了"每次重新设计"，却把设计决策的载体（不落文件）、可复用物（禁止读 notes/旧成品/母版）
> 和设计工具（一半字段不生效）全部堵死，只留下上一份脚本和一份 Golden Sample 作为唯一参照；
> 同时把质量验证全部交给人工。
> 于是"套用上一份"和"排版反复出问题"不是执行者的疏忽，而是当前结构的**必然输出**。

> **二轮补记（v0.9.0）**：R3 / R4 / R5 三处结构性缺口已补——设计决策有了落盘载体
> （`design.json`）、内容层有了带诊断的正式解析器、质量验证有了八维 QA 与确定性 auto-fit。
> 「一键达标生成」在结构上已成立（复合定制版实测首轮达标、零后处理）。
> R1（Golden Sample 的制度性诱导）与 R2（设计空间 ≫ 渲染能力）仍未从根上解决，
> R6（作者身份通道）仍待用户决策——这三项才是下一轮的主战场。
